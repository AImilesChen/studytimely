# V2.0.1 — confirm once when creating an account

Existing Google-linked accounts now proceed straight through Google sign-in. The login page no longer requires an age/policy checkbox before the Google button can be used. Existing email-account recovery and community-profile edits also stop repeating the first-registration declaration.

After Google verifies a new identity, the user receives a ten-minute browser-bound pending-registration proof and returns to a short account-setup form. An account and its session are created only after explicit acceptance of the existing 16+ account requirements and current policy. The account records the actual acceptance time and policy version; historical timestamps are not invented for existing accounts. Cancelling setup creates no new account. First community participation still asks for the community rules, and public ranking remains off by default.

Pending registration is not account authentication. Its token is random, HttpOnly, Secure on HTTPS and stored only as a hash in D1. Completion/cancellation requires same-origin and a separate CSRF value. Account insertion, session insertion and proof consumption are transactional; replay and concurrent submissions cannot issue duplicate sessions. Google token verification, browser-bound OAuth state, PKCE, explicit old-account linking and the `openid email` scope are retained. No Google credential, callback, moderator permission or minimum-age policy changes are required.

Additive migration `0004_registration_confirmation.sql` creates pending transactions and nullable acceptance fields. Expired transactions are unusable after ten minutes and removed during setup housekeeping or daily maintenance. Public privacy/cookie notices describe this temporary processing. Pending identities cannot access cloud records or community participation before account creation.

Validation before rollout: 85 automated tests passed. Actual isolated local Worker/D1 integration covered non-authenticating pending proofs, explicit acceptance, session creation, replay prevention, exported acceptance records and removal of only its disposable synthetic account. Browser QA covered cancellation and successful first setup. A 390×844 view had one H1, one setup checkbox and document width 375 without horizontal document overflow. Synthetic local identities are not evidence of real Google login.

Production rollout and real Google acceptance are recorded separately after observation. Main promotion remains subject to the existing real-login/community acceptance gate; no successful production Google login is inferred from installation or synthetic tests.
