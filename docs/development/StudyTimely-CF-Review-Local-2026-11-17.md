## Implemented behavior

The detection copy normalises NFKC and removes invisible formatting. Punctuation/spacing joins are used only for targeted pattern detection; original approved text is retained for storage and display. Rules now cover separated or disguised contact channels, dating invitations, euphemistic sexual/image solicitation, exam-answer sales and directed threats. They are exercised against educational history, biology, psychology, computing and chemistry contexts. This is a bounded rule set, not a claim that every obfuscation can be recognised.

The reviewer is selected explicitly. Cloudflare uses the AI binding and fixed model @cf/meta/llama-guard-3-8b, a short study-writing user prompt followed by the proposed post as an assistant output, deterministic settings, a 24-token output bound and JSON response format. Text remains capped at 500 characters and 2,000 UTF-8 bytes. A detection copy, not account, room, invitation or learning metadata, enters the provider payload. Strict safe/category consistency and token/Neuron telemetry validation are required. Azure remains a separately configured legacy option; there is no automatic provider fallback or unsafe local-only fallback.

Local policy violations are rejected before provider calls. Only a fully approved message may reach chat storage/broadcast, with the existing second membership/session/mute/closure check after the asynchronous review. A blocked message produces the sender-only *** notice and keeps the editable draft. Errors, malformed output, missing configuration or exhausted capacity pause sending. Unknown or late provider completion cannot publish a message.

Cloudflare's candidate app budget defaults to 5,000 Neurons per UTC day, configurable between 300 and 8,000. Each call atomically reserves 300 units before inference. Known usage settles conservatively to rounded-up units using the greater of provider Neurons and the documented token conversion. Successful/blocked calls release unused reservation; errors with unknown usage charge the full reservation, and an interrupted pending request retains its reservation. Settlement is idempotent. Failed review opens a one-minute circuit; rate limits remain four provider attempts/second account-wide, three chat attempts/ten seconds and thirty/hour per member. These application counters are not the Cloudflare account's free balance and cannot guarantee zero overage when other projects share usage or prices/telemetry change.

The room interface identifies the configured reviewer, explains what text is sent, pauses the composer when capacity/review is unavailable and provides Check availability. Platform moderators can open Review capacity beside Review reports: the panel shows remaining app budget, pending reservations and today's checks, with failure/shared-account explanations. Ordinary members and room owners do not receive private capacity counters. GET /api/community/review-status returns 401 anonymously, 403 for a non-platform member, and private no-store/noindex data for the configured platform moderator. Moderator counters describe review outcomes, not successful message publication.

The privacy policy candidate identifies Cloudflare and Azure paths, normalised detection copies and short-lived usage metadata. Private activity task/reflection fields are still not submitted to either external reviewer. No dependency, analytics, protected Sites adapter, authentication, ranking or free room-limit changes were made.

## Expanded actual-provider evaluation

The corpus has 200 synthetic cases from 50 base statements, each in plain, invisible-character, fullwidth and contextual variants. It is a purposive regression set, not 200 independent observations. The original split was 96 development and 104 holdout cases.

Initially 80 cases were blocked locally and 120 direct CF requests were made through the actual application review adapter with an isolated in-memory D1 budget and an AI.run-to-REST bridge. After 28 requests one normal-context case returned REVIEW_UNAVAILABLE. The run stopped and its original ledger was preserved. That attempt had no usable provider response/usage; the initial harness did not capture whether this was transport, timeout or result failure. Do not label it an identified timeout. Metadata-only diagnostic stages have since been added, without text or raw provider response logging.

Untested cases were then continued within the same total120-call approval, without retrying or erasing the unavailable case. Checkpoint cost/attempt values were restored conservatively; the diagnostic run's old allowed-outcome count was not reconstructed, so its raw post-resume allowed counter is not a full-run outcome tally. Classification results are taken from the case ledger; actual fresh-D1 counter correctness is verified independently by the local integration test.

The initial expanded result was 195 matching case outcomes: one unavailable normal case and four Chinese threat variants of one base statement were unresolved/missed. No other answered normal case was blocked. The newly observed directed-threat pattern was added locally and verified to reject all four variants before CF/storage. Replaying current rules with the recorded live verdicts gives 199 matching classifications and one retained unavailable outcome, with no extra inference. The holdout was used to make that correction and is therefore no longer an untouched generalisation test. No claim of 100% moderation accuracy or 200 new successful CF responses is made.
